## 2. 前置认知



**前置**：L08 BAR——枚举后每个 BAR 有 start/end/flags。但这些地址之间可能冲突。

**核心问题**：内核用 `struct resource` 树管理所有系统资源（物理内存、IO 端口、MMIO 空间）。PCI 的 BAR 地址必须挂到这棵树的 `iomem_resource` 分支下，冲突检测只在这棵树上生效。

## 3. 核心原理

### 2.1 全局资源树

```
/iomem_resource (根)
  ├─ 00000000-DFFFFFFF : PCI Bus 0000:00
  │    ├─ E0000000-EFFFFFFF : PCI MMCONFIG 0000 [bus 00-7f]
  │    ├─ F0000000-F01FFFFF : PCI Bus 0000:02
  │    │    └─ F0000000-F00FFFFF : 0000:02:00.0 (BAR0)
  │    └─ FFE00000-FFFFFFFF : 0000:00:1f.0 (ICH)
  └─ 100000000-1FFFFFFFF : System RAM
```

每个 `struct resource` 有 parent 指针，形成严格的层级树。兄弟节点不能重叠——`request_resource()` 会拒绝重叠请求。

### 2.2 资源类型

| flag | 含义 | 对应 `/proc/` |
|------|------|-------------|
| `IORESOURCE_MEM` | MMIO 地址 | `/proc/iomem` |
| `IORESOURCE_IO` | IO 端口 | `/proc/ioports` |
| `IORESOURCE_PREFETCH` | 可预取 MMIO | |
| `IORESOURCE_MEM_64` | 64-bit BAR | |
| `IORESOURCE_BUSY` | 已被 driver 占用 | |

### 2.3 冲突检测

`request_mem_region()` → `__request_region()` → `__request_resource(parent, res)` → 遍历 parent 的子节点 → 检测与 `res` 是否重叠。重叠 → 返回 `-EBUSY`。这是内核防止两个驱动映射同一块 MMIO 的机制。

### 2.4 资源重分配：`__pci_bus_size_bridges()`

有时 BIOS 给的 BAR 地址不合理——空间太小、冲突。内核的 PCI 资源重分配算法在 `setup-bus.c` 中：

1. **计算需求**：`__pci_bus_size_bridges()` 遍历每个 bus 上的每个设备，累加各 BAR 的大小需求
2. **分配地址**：`pci_bus_assign_resources()` 从父资源窗口向下逐层分配
3. **写入硬件**：把计算得来的新地址写入设备的 BAR 寄存器

重分配触发条件：内核参数 `pci=realloc` 或检测到 BAR 地址冲突。

## 4. 内核源码带读

> x86_64 v7.0。`struct resource` 树操作 + 冲突检测的关键路径。

### 3.1 `request_resource()` —— 资源冲突检测

源码：`kernel/resource.c`。遍历兄弟节点，检查 `res->start/end` 是否与已有资源重叠。重叠 → `-EBUSY`。`request_mem_region()` → `__request_region(&iomem_resource, ...)` 是对它的封装。

### 3.2 `__pci_bus_size_bridges()` —— bridge 窗口大小计算

源码：`setup-bus.c:1388`。两阶段：第一阶段自底向上计算每个 bridge 下游 BAR 所需的总空间；第二阶段自顶向下将窗口空间分配给下游设备。

### 3.3 `pci_bus_assign_resources()` —— 新地址写入硬件

源码：`setup-bus.c:1504`。遍历每个 bridge → 对每个子设备调 `pci_assign_resource()` → `pci_update_resource()` → 直接写设备 BAR 寄存器。

**⚠ x86 专属**：`/proc/iomem` 是全局 `iomem_resource` 树的文本导出。`request_mem_region` 冲突是 BAR 地址重叠的报警器——如果两个设备被 BIOS 分配了相同的 BAR 地址，第二个设备的 probe 在这里失败。x86 服务器的多 segment 场景下，每个 domain 有独立的 `iomem_resource` 分支。
## 5. x86 关联

x86 上 `/proc/iomem` 能看到完整的系统内存映射。BIOS 通常把 PCI MMIO 空间放在 `0xE0000000` 附近以下，物理 RAM 放在低位（`0x00000000-0xDFFFFFFF`）。多 socket 服务器上每个 CPU 有自己的 PCI segment 和对应的 `iomem_resource` 分支。

## 6. GPU 关联

GPU 的大 BAR（framebuffer 256MB+）是系统资源主要的消费者之一。`request_mem_region` 失败 → `ioremap` 失败 → probe 拿不到 BAR → 返回 -ENOMEM → GPU 不可用。排查：`cat /proc/iomem | grep -A 10 nvidia`。

## 7. 思考题

1. `request_resource()` 和 `request_mem_region()` 的关系是什么？为什么驱动通常调后者？
2. `__pci_bus_size_bridges()` 之后，bridge 的窗口（MMIO base/limit）可能被重新计算。这个重计算会改变 `BAR 的物理地址`吗？
3. 两个 PCI 设备被 BIOS 分配了重叠的 MMIO 空间——`request_mem_region()` 返回什么？设备能正常工作吗？

## 6b. 参考答案

**Q1**：`request_mem_region()` 是封装——创建 `IORESOURCE_MEM` 类型 resource，然后调用 `__request_region(&iomem_resource, res)`。驱动调 `request_mem_region` 因为它自动处理类型标记，调用者不需要知道全局 `iomem_resource` 根节点的存在。

**Q2**：会。内核重计算后通过 `pci_bus_assign_resources()` 把新地址写入 bridge 的窗口和设备的 BAR 寄存器。重启前后同一个设备的 BAR 物理地址可能不同。这对验证有影响——不能假设重启后 BAR 地址不变。

**Q3**：第一个 `request_mem_region()` 返回成功，第二个返回 `-EBUSY`（冲突）。第一个设备可以正常 `ioremap` 使用，第二个设备的驱动 probe 失败（`pci_request_regions()` 返回 -EBUSY）→ 第二个设备在工作。这就是"双设备地址冲突"的典型症状——`lspci -vv` 显示两个设备 BAR 起始地址重叠。

## 8. 渐进式代码构建

```c
// 在 probe 中请求 BAR 区域（运行在已 probe 的设备上）
ret = pci_request_regions(dev, "pci_demo");
if (ret) pr_err("L09: request_regions failed %d\n", ret);
else pr_info("L09: BAR regions requested successfully\n");
pci_release_regions(dev);  // remove 对应
```
